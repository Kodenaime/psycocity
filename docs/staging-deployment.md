# Staging deployment and rollback

This repository has executable container definitions, not a deployed environment. Hosting, registry, DNS/TLS, provider accounts and secrets must be supplied. No cloud resources have been purchased or provisioned.

Use a separate TLS replica-set MongoDB database and least-privilege database user, private Cloudinary cloud, verified Resend sender/domain and Paystack **test** integration. Never restore production data into an internet-accessible testing environment. Set the private values in `deploy/staging.env.example` in a secret manager/file outside Git. Stable `OUTBOX_ENCRYPTION_KEY` encrypts MFA and queued mail: back it up separately and never generate a new value on rollout. `POLICIES_APPROVED=false` intentionally blocks public registration until policies are approved. The application refuses live payment secrets and production launch; staging runs production builds with explicitly isolated test payment configuration.

1. Run `npm ci` and `npm run check` at the reviewed revision. CI runs the same gate. Read test reports; injected provider fixtures do not prove external delivery/settlement.
2. Build `docker build -t psycocity:REVIEWED_SHA .`; inspect/image-scan it, push to your private registry and record the immutable digest. Never embed environment files in images. Retain the preceding digest.
3. On the staging host, set `IMAGE=registry/image@sha256:...` and `STAGING_ENV_FILE=/secure/staging.env`. Validate `docker compose -f deploy/compose.staging.yml config --quiet` (never print the interpolated secret configuration).
4. Before rollout, take a database backup and demonstrate a restore to a different isolated database. Read `docs/recovery-runbook.md`. Index setup is additive and repeatable; no startup migration deletes data or indexes.
5. Run `docker compose -f deploy/compose.staging.yml up -d`. The migration service must succeed before web/workers start. Check migration exit status and `/api/v1/ready` through the external HTTPS origin. A database ping is readiness, not a complete provider health assertion.
6. Terminate TLS at a managed reverse proxy; forward to loopback:3001, reject unexpected hosts, limit bodies to 10 MB and configure request timeouts. Do not expose MongoDB/container ports publicly. Express intentionally does not trust arbitrary forwarded IPs. Set `TRUST_PROXY_CIDRS` to only the verified proxy peer IPs/narrow CIDRs after checking the host architecture, otherwise leave it blank. Keep direct client access to application ports closed; never use blanket proxy trust.
7. Bootstrap individual staff using the documented trusted CLI, enroll MFA, then run the live-testing checklist against staging. Check mail/payments worker uptime and queues; healthy web alone does not prove workers are healthy. Monitor ready failures, redacted errors, failed notification count and oldest unresolved payments. Send alerts through your hosting monitor to a named operator; no alert destination is configured here.
8. For rollback, retain the current DB and encryption key. Set `IMAGE` to the preceding known-good digest and recreate web/workers, then verify readiness and the affected private journeys. Additive new collections/fields remain; do not down-migrate or restore a backup over the active database. Never roll back past a security fix without incident-owner approval.

GitHub CI builds and verifies source but does not auto-deploy without a selected hosting target. Configure an environment-protected deploy job only after registry/host credentials and approval policy are known. Record provider/webhook reachability, deployment digest, index output, rollout/rollback evidence and owners in the launch checklist. Remote staging deployment, external provider checks and managed backup restoration are blocked until those resources exist.

Local configuration syntax was checked with a placeholder image and the example environment file using `config --quiet`; that does not validate supplied credentials or the remote host. Docker builds also require registry/npm network access inside the build container, independently of the workspace's npm connectivity.

Corporate build networks can supply a trusted CA with BuildKit `--secret id=build_ca,src=/trusted/ca.pem` and standard proxy build arguments. The optional CA is mounted only during dependency installation; it is not copied into the runtime image. Do not disable TLS verification. This cloud builder's initial attempts failed to resolve its proxy hostname. Supplying its resolved build-only proxy host mapping and optional CA secret allowed the image to build with TLS verification intact. The image then passed a local isolated non-root/read-only production-runtime smoke without publishing a port; no remote rollout or provider test was performed.
